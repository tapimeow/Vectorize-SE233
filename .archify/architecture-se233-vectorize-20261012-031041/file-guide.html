📘 File guide: what each file does, and how and why the files connect

📘 คู่มือไฟล์: แต่ละไฟล์ทำอะไร เชื่อมกันยังไง และทำไมถึงออกแบบแบบนี้

The big idea in 30 seconds

สรุปภาพรวมใน 30 วินาที

The app is split into layers, and each layer only talks to the layer below it:

แอปนี้แบ่งเป็นชั้น ๆ (layer) แต่ละชั้นคุยกับชั้นที่อยู่ถัดลงไปเท่านั้น:

  1. View (VectorizeView): only draws the screen. It has no logic.
  2. Controller (VectorizeController): listens to clicks and drops, then decides what should happen.
  3. Coordinator (ProcessingCoordinator): moves heavy work off the UI thread into background Tasks, and brings results back.
  4. Services (service/*): do the real work: read files, unzip, prepare pixels, check the SVG, write files.
  5. Adapter (AutoTraceVectorEngine): the only class that talks to the external autotrace program.
  6. Model (model/*): plain data (images, settings, status) that every layer shares.
  1. View (VectorizeView): วาดหน้าจออย่างเดียว ไม่มี logic
  2. Controller (VectorizeController): รอฟังการคลิก/ลากวาง แล้วตัดสินว่าจะให้เกิดอะไรขึ้น
  3. Coordinator (ProcessingCoordinator): ย้ายงานหนักออกจาก UI thread ไปทำใน Task เบื้องหลัง แล้วส่งผลกลับมา
  4. Services (service/*): ทำงานจริง เช่น อ่านไฟล์, แตก zip, เตรียมพิกเซล, ตรวจ SVG, เขียนไฟล์
  5. Adapter (AutoTraceVectorEngine): คลาสเดียวที่คุยกับโปรแกรม autotrace ภายนอก
  6. Model (model/*): ข้อมูลล้วน ๆ (รูป, settings, สถานะ) ที่ทุกชั้นใช้ร่วมกัน
Why layers? (1) The UI never freezes, because slow work never runs on the JavaFX thread. (2) Each piece can be tested alone: tests call services directly, with no UI. (3) Swapping the tracing engine only touches one class.
ทำไมต้องแบ่งชั้น? (1) UI ไม่ค้าง เพราะงานช้า ๆ ไม่เคยรันบน JavaFX thread (2) เทสต์แยกแต่ละส่วนได้ เทสต์เรียก service ตรง ๆ ไม่ต้องเปิด UI (3) อยากเปลี่ยน engine ที่ใช้ trace ก็แก้แค่คลาสเดียว

🔁 The 3 main flows, step by step

🔁 3 flow หลัก ทีละขั้น

① Import (drop files)

① Import (ลากไฟล์เข้ามา)

  1. VectorizeView.onDrop gets the dropped files as List<Path>.
  2. VectorizeController.importPaths shows "Importing…", then calls coordinator.importAsync.
  3. The coordinator wraps the work in a Task and runs it on a worker thread.
  4. On the worker, ImageImportService.importPaths runs. ZIP files go to ZipImportService.extract. Each image is checked by validateImage.
  5. It returns an ImportResult holding the good documents plus a list of errors. One bad file does not cancel the others.
  6. Back on the FX thread (setOnSucceeded), the controller adds the documents to AppSession, switches to the editor and calls coordinator.preprocess to make the previews.
  1. VectorizeView.onDrop รับไฟล์ที่ลากมาเป็น List<Path>
  2. VectorizeController.importPaths โชว์ "Importing…" แล้วเรียก coordinator.importAsync
  3. coordinator ห่องานไว้ใน Task แล้วส่งไปรันบน worker thread
  4. บน worker: ImageImportService.importPaths ทำงาน ถ้าเป็น ZIP ส่งให้ ZipImportService.extract แล้วเช็กทุกรูปด้วย validateImage
  5. ได้ ImportResult กลับมา = รูปที่ดี + รายการ error ไฟล์เสียไฟล์เดียวไม่ทำให้ไฟล์อื่นพัง
  6. กลับมาที่ FX thread (setOnSucceeded) controller เอารูปใส่ AppSession, เปลี่ยนไปหน้า editor แล้วเรียก coordinator.preprocess เพื่อทำพรีวิว

② Preview (change a setting)

② Preview (เปลี่ยน setting)

  1. The user changes Detail, Color mode, the number of colors, or Remove Background. A listener in wire() fires.
  2. changeSettings builds a new VectorizationSettings (immutable) and sets it on the selected ImageDocument. That bumps the document's generation number.
  3. coordinator.refresh → schedulePreview cancels the old preview Task, takes a snapshot (path, settings, generation) and starts a new Task.
  4. On the worker, VectorizationService.convert runs: read the image → RasterPreprocessor.prepare → write a temporary PNG → engine.trace → validator.validate.
  5. Back on FX: the result is stored only if the generation still matches. An old, slow result is thrown away. Then showSelected → view.showSvg.
  1. ผู้ใช้เปลี่ยน Detail / Color mode / จำนวนสี / Remove Background → listener ใน wire() ทำงาน
  2. changeSettings สร้าง VectorizationSettings ตัวใหม่ (immutable) แล้วใส่ให้ ImageDocument ที่เลือกอยู่ → เลข generation ของรูปเพิ่มขึ้น
  3. coordinator.refresh → schedulePreview ยกเลิก Task พรีวิวตัวเก่า เก็บ snapshot (path, settings, generation) แล้วเริ่ม Task ใหม่
  4. บน worker: VectorizationService.convert = อ่านรูป → RasterPreprocessor.prepare → เขียน PNG ชั่วคราว → engine.trace → validator.validate
  5. กลับมาที่ FX: เก็บผลเฉพาะตอนที่ generation ยังตรงกัน ถ้าเป็นผลเก่าที่มาช้าจะโดนทิ้ง แล้ว showSelected → view.showSvg

③ Export All

③ Export All

  1. exportAll() in the controller opens a DirectoryChooser on FX. Native dialogs must run on the FX thread.
  2. coordinator.exportAll takes an ExportItem snapshot of each image on FX. The worker never touches the mutable ImageDocument.
  3. ProcessingPolicy decides whether each image goes to the parallel workers pool or the one-at-a-time serial executor.
  4. ExportService.exportOne reuses the cached SVG if it is still fresh, otherwise converts again. Then it validates again, reserves a unique name, writes a temp file and moves it into place.
  5. Each Task's success, failure or cancel updates a shared Batch counter, and the UI shows "Exporting: 3 of 5".
  1. exportAll() ใน controller เปิด DirectoryChooser บน FX (dialog ของระบบต้องเปิดบน FX thread)
  2. coordinator.exportAll ทำ snapshot เป็น ExportItem ของแต่ละรูปบน FX เพื่อให้ worker ไม่ไปแตะ ImageDocument ที่แก้ไขได้
  3. ProcessingPolicy ตัดสินว่ารูปไหนไป pool workers (รันขนาน) หรือ serial (ทีละรูป)
  4. ExportService.exportOne: ถ้า SVG ที่ cache ไว้ยังใหม่ก็ใช้เลย ไม่งั้น convert ใหม่ → ตรวจอีกรอบ → จองชื่อไฟล์ที่ไม่ซ้ำ → เขียนไฟล์ temp แล้วย้าย
  5. Task แต่ละตัว สำเร็จ/พัง/ยกเลิก จะไปอัปเดตตัวนับ Batch แล้ว UI โชว์ "Exporting: 3 of 5"

🧵 Thread rules (the most likely presentation question)

🧵 กฎเรื่อง thread (น่าจะโดนถามตอนพรีเซนต์มากที่สุด)

Runs on the JavaFX threadรันบน JavaFX threadRuns on worker threadsรันบน worker thread
Everything in View and Controller; Task callbacks (setOnSucceeded/Failed/Cancelled); file/folder choosers; changes to ImageDocument and AppSession ทุกอย่างใน View/Controller, callback ของ Task (setOnSucceeded/Failed/Cancelled), dialog เลือกไฟล์/โฟลเดอร์, การแก้ ImageDocument และ AppSession Reading images, unzipping, preprocessing, running autotrace, validating, writing SVG and preset files อ่านรูป, แตก zip, preprocess, รัน autotrace, ตรวจ SVG, เขียนไฟล์ SVG/preset
Why? JavaFX is single-threaded: UI objects may only be touched on the FX thread, and if that thread is busy the window freezes. A Task runs call() on a worker and then fires its handlers back on the FX thread automatically, so that is the safe bridge between the two. Because the handlers always run on FX, plain HashMap/ArrayList fields in the coordinator are safe without locks.
ทำไม? JavaFX เป็น single-thread: แตะ UI ได้เฉพาะบน FX thread และถ้า thread นี้ไม่ว่าง หน้าต่างจะค้าง Task รัน call() บน worker แล้วเรียก handler กลับมาบน FX thread ให้อัตโนมัติ เลยเป็นสะพานที่ปลอดภัยระหว่างสองฝั่ง และเพราะ handler รันบน FX เสมอ field อย่าง HashMap/ArrayList ใน coordinator เลยไม่ต้องใส่ lock

VectorizeApplication.java Mona

se233/vectorize/VectorizeApplication.java

The wiring point of the whole app. In start(stage) it creates the objects in dependency order: ZipImportService → AutoTraceVectorEngine → VectorizationService(engine) → ProcessingCoordinator(vectorization) → VectorizeView(stage) → VectorizeController(view, coordinator, new ImageImportService(zip)). In stop() it closes the coordinator (stops its threads) and the zip service (deletes its temporary folders).

จุดประกอบทั้งแอป ใน start(stage) จะสร้าง object ตามลำดับที่ต้องใช้กัน: ZipImportService → AutoTraceVectorEngine → VectorizationService(engine) → ProcessingCoordinator(vectorization) → VectorizeView(stage) → VectorizeController(view, coordinator, new ImageImportService(zip)) ส่วนใน stop() จะปิด coordinator (หยุด thread) และ zip service (ลบโฟลเดอร์ชั่วคราว)

Why build everything here? Dependencies are passed in through constructors, so you can see the whole object graph in three lines. It also lets tests build the same objects with a fake engine.
ทำไมสร้างทุกอย่างตรงนี้? ส่ง dependency ผ่าน constructor ทำให้เห็นโครงสร้าง object ทั้งหมดในสามบรรทัด และเทสต์ก็สร้าง object ชุดเดียวกันได้โดยใช้ engine ปลอมแทน

module-info.java Shared

The Java module descriptor. It requires javafx.controls, javafx.web (for WebView), java.desktop (for BufferedImage/ImageIO) and java.xml (for SVG parsing), and exports the packages so JavaFX and the tests can reach them.

ไฟล์ประกาศ module ของ Java มี requires javafx.controls, javafx.web (สำหรับ WebView), java.desktop (สำหรับ BufferedImage/ImageIO), java.xml (สำหรับ parse SVG) และ exports package ต่าง ๆ ให้ JavaFX กับเทสต์เข้าถึงได้

  • showOriginal(path): new Image(url, true) = โหลดรูปเบื้องหลัง FX ไม่ค้าง

ถาม: ทำไมใช้ WebView แสดง SVG? JavaFX ไม่มีตัวแสดงไฟล์ SVG ในตัว แต่ WebView แสดง SVG จริงได้ และเราปิด script ไว้ SVG ที่มีโค้ดอันตรายเลยรันอะไรไม่ได้

Model (ข้อมูลที่ใช้ร่วมกัน)

AppSession.java

The list of loaded ImageDocuments plus selectedIndex. It has canBack/canNext/back/next, and back/next throw if you go past either end. documents() returns a copy (List.copyOf) so nobody outside can change the list by accident.

รายการ ImageDocument ที่โหลดแล้ว + selectedIndex มี canBack/canNext/back/next ถ้าเลื่อนเลยหัวหรือท้าย back/next จะ throw ส่วน documents() คืนสำเนา (List.copyOf) คนข้างนอกจะได้แก้ list ไม่ได้โดยไม่ตั้งใจ

ImageDocument.java

One image: source path, displayName, settings, status, svg, detectedColors, error, progress, plus a generation counter. Calling settings(new) increments the generation and resets the status to QUEUED. hasCurrentResult() is true only if the SVG was made with the current settings.

รูปหนึ่งรูป: path source, displayName, settings, status, svg, detectedColors, error, progress และตัวนับ generation เรียก settings(ใหม่) เมื่อไหร่ generation จะเพิ่มขึ้นและสถานะกลับเป็น QUEUED ส่วน hasCurrentResult() จะเป็น true เฉพาะตอนที่ SVG ทำมาจาก settings ปัจจุบัน

Why a generation? If the user changes settings twice quickly, the first Task may finish last. Comparing generations means an outdated result never overwrites a newer one.
ทำไมต้องมี generation? ถ้าผู้ใช้เปลี่ยน settings สองครั้งติดกัน Task ตัวแรกอาจเสร็จทีหลัง พอเทียบ generation ผลที่ล้าสมัยก็จะไม่ไปทับผลที่ใหม่กว่า

VectorizationSettings.java record

An immutable record: detail, colorMode, customColors (validated to be 2–5) and removeBackground. defaults() is Medium / Custom / 2 / false. The withX() methods return a new copy with one field changed.

record ที่แก้ไม่ได้ (immutable): detail, colorMode, customColors (ต้องอยู่ระหว่าง 2–5) และ removeBackground ส่วน defaults() = Medium / Custom / 2 / false และ method withX() จะคืนสำเนาใหม่ที่เปลี่ยนไปหนึ่งค่า

Why immutable? A worker thread can read it safely while the user changes the UI, because nobody can modify an existing object. It also makes equals() free, which is how "is this result still current?" gets checked.
ทำไมต้อง immutable? worker thread อ่านได้อย่างปลอดภัยแม้ผู้ใช้กำลังเปลี่ยน UI อยู่ เพราะไม่มีใครแก้ object เดิมได้ แถมได้ equals() มาฟรี ซึ่งใช้เช็กว่า "ผลนี้ยังเป็นของ settings ปัจจุบันไหม"

DetailLevel / ColorMode / ProcessingStatus

DetailLevel LOW/MEDIUM/HIGH maps to a resize cap (maxDimension 360/640/960px) and an autotrace curveError (0.5/0.25/0.1, where smaller means it follows edges more closely). ColorMode is UNLIMITED or CUSTOM. ProcessingStatus is QUEUED, RUNNING, READY, FAILED or CANCELLED.

DetailLevel LOW/MEDIUM/HIGH → ขนาดสูงสุดที่ย่อรูป (maxDimension 360/640/960px) + ค่า curveError ของ autotrace (0.5/0.25/0.1 ยิ่งน้อยยิ่งตามขอบละเอียด) ส่วน ColorMode = UNLIMITED หรือ CUSTOM และ ProcessingStatus = QUEUED, RUNNING, READY, FAILED, CANCELLED

Why enums? Type-safe: you can't pass "medum" by mistake, and the combo boxes fill directly from values().
ทำไมใช้ enum? type-safe พิมพ์ผิดเป็น "medum" ไม่ได้ และ combo box ก็เติมค่าจาก values() ได้เลย

ConversionException.java Shared

se233/vectorize/exception/ConversionException.java

A checked exception (it extends Exception) with a Kind: INPUT, ZIP, ENGINE, SVG, OUTPUT or CANCELLED. Every service throws it with a message the user can read. The coordinator's message() shows that message as-is; any other exception becomes "Unexpected error: …".

exception แบบ checked (extends Exception) ที่มี Kind: INPUT, ZIP, ENGINE, SVG, OUTPUT, CANCELLED ทุก service จะ throw ตัวนี้พร้อมข้อความที่ผู้ใช้อ่านเข้าใจ message() ใน coordinator จะโชว์ข้อความนั้นตรง ๆ ส่วน exception แบบอื่นจะกลายเป็น "Unexpected error: …"

Why checked, and why a Kind? Checked means the compiler forces callers to handle the failure. Kind lets the code tell "file is corrupt" apart from "autotrace missing" or "can't write the folder" without parsing message strings.
ทำไมเป็น checked และมี Kind? checked = compiler บังคับให้คนเรียกต้องจัดการ error ส่วน Kind ช่วยแยกว่า "ไฟล์เสีย" ต่างจาก "ไม่มี autotrace" หรือ "เขียนโฟลเดอร์ไม่ได้" โดยไม่ต้องไปอ่านข้อความ

The bridge between the UI and the workers. It has two executors:

Important details

รายละเอียดสำคัญ

  • Snapshot before submitting: the path, settings and generation are copied on FX, and the worker only uses those copies.
  • previews map: one preview Task per document. A new one cancels the old one.
  • active list: tracks running Tasks for Cancel. A state listener removes each Task when it finishes.
  • Batch: counters for completed, failed and cancelled jobs. It's only changed inside FX handlers, so no locks are needed. The counted flag makes sure each Task is counted once.
  • One failed image doesn't stop the others: each Task has its own failure handler.
  • snapshot ก่อนส่งงาน: path, settings, generation ถูกคัดลอกไว้บน FX แล้ว worker ใช้แค่สำเนาพวกนั้น
  • map previews: หนึ่งรูปมีพรีวิว Task ได้ตัวเดียว ตัวใหม่มาจะยกเลิกตัวเก่า
  • list active: เก็บ Task ที่รันอยู่ไว้ให้ปุ่ม Cancel ใช้ และมี listener ของ state คอยลบออกตอน Task จบ
  • Batch: ตัวนับงานที่เสร็จ/พัง/ยกเลิก แก้แค่ใน handler บน FX เลยไม่ต้องใช้ lock ส่วน flag counted กันไม่ให้นับ Task เดียวซ้ำ
  • รูปหนึ่งพังไม่ทำให้รูปอื่นหยุด เพราะแต่ละ Task มี failure handler ของตัวเอง

ถาม: กด Cancel แล้ว autotrace หยุดได้ยังไง? task.cancel(true) → isCancelled() เป็น true → ค่านี้คือ BooleanSupplier cancelled ที่ส่งต่อลงไป → AutoTraceVectorEngine เช็กทุก 100 ms แล้ว kill process ใน finally

The pipeline conductor. convert(source, settings, cancelled, stage):

ตัวคุม pipeline convert(source, settings, cancelled, stage):

  1. Check cancel, then read the image (ImageIO.read) and compute its sourceVersion (file size + last-modified time).
  2. preprocessor.prepare(image, settings)
  3. Write the prepared image to a temporary PNG.
  4. engine.trace(tempPng, settings, ignoredColor, cancelled)

  2. preprocessor.prepare(image, settings)
  3. เขียนรูปที่เตรียมแล้วเป็น PNG ชั่วคราว
  4. engine.trace(tempPng, settings, ignoredColor, cancelled)
  5. validator.validate(svg)
  6. คืน ConversionResult (svg, detectedColors, sourceVersion, PIPELINE_VERSION) และไฟล์ชั่วคราวจะถูกลบใน finally เสมอ

stage.accept("Tracing vectors") and similar calls report honest stage names. We don't invent fake percentages.

stage.accept("Tracing vectors") และอื่น ๆ บอกชื่อขั้นตอนตามจริง ไม่ได้มั่วเปอร์เซ็นต์ขึ้นมา

RasterPreprocessor.java Day

Prepares the pixels before tracing. prepare(image, settings):

เตรียมพิกเซลก่อน trace prepare(image, settings):

  1. Scale the image so its longest side is at most detail.maxDimension() (bilinear smoothing also softens noise).
  2. Mask the background first with BackgroundRemovalService.mask.
  3. Analyze colors with ColorAnalysisService.analyze, skipping the masked pixels.
  4. In Custom mode only, snap every pixel to its nearest palette color. Unlimited keeps the original colors.
  5. Paint the background pixels with a color no foreground pixel uses (magenta-ish), and return it as ignoredColor so autotrace skips it. The result is a transparent background in the SVG.
  1. ย่อรูปให้ด้านที่ยาวที่สุดไม่เกิน detail.maxDimension() (ย่อแบบ bilinear ช่วยลด noise ไปด้วย)
  2. ทำ mask พื้นหลังก่อนด้วย BackgroundRemovalService.mask
  3. วิเคราะห์สีด้วย ColorAnalysisService.analyze โดยข้ามพิกเซลที่ถูก mask
  4. เฉพาะโหมด Custom: เปลี่ยนทุกพิกเซลเป็นสีใน palette ที่ใกล้ที่สุด ส่วน Unlimited ใช้สีเดิม
  5. ทาพิกเซลพื้นหลังด้วยสีที่ไม่มี foreground ใช้ (โทนม่วงชมพู) แล้วส่งค่าออกไปเป็น ignoredColor ให้ autotrace ข้ามสีนี้ ผลคือ SVG มีพื้นหลังโปร่งใส
Why mask before quantizing? If you reduce to 2 colors first, a white background and a light-grey shape might merge into one color and the shape would be deleted along with the background.
ทำไม mask ก่อนลดสี? ถ้าลดเหลือ 2 สีก่อน พื้นหลังสีขาวกับรูปทรงสีเทาอ่อนอาจรวมเป็นสีเดียวกัน แล้วรูปทรงก็จะโดนลบไปพร้อมพื้นหลัง

BackgroundRemovalService.java Day

mask(image, remove) returns a boolean[] where true means "not foreground". Fully transparent PNG pixels are always masked. If removal is on, it:

mask(image, remove) คืน boolean[] โดย true = "ไม่ใช่ foreground" พิกเซล PNG ที่โปร่งใสทั้งหมดจะถูก mask เสมอ ถ้าเปิด Remove Background จะ:

  1. Groups the border pixels into rough color buckets and picks the most common one.
  2. Gives up if that color covers less than 60% of the border, because it's probably a photo with no clear background.
  3. Runs a flood fill (BFS) from the border through similar neighbours (±24 per RGB channel).
  1. จัดกลุ่มสีของพิกเซลที่ขอบรูปแบบคร่าว ๆ แล้วเลือกกลุ่มที่เจอบ่อยที่สุด
  2. ถ้าสีนั้นมีไม่ถึง 60% ของขอบ จะไม่ลบ (น่าจะเป็นรูปถ่ายที่ไม่มีพื้นหลังชัด ๆ)
  3. ทำ flood fill (BFS) จากขอบ ลามไปยังพิกเซลข้าง ๆ ที่สีใกล้กัน (ต่างกันไม่เกิน ±24 ต่อช่อง RGB)
Why flood fill and not "delete every white pixel"? Only regions connected to the edge are removed, so white eyes inside a logo stay.
ทำไมใช้ flood fill แทน "ลบสีขาวทั้งหมด"? ลบเฉพาะส่วนที่ต่อกับขอบรูป ตาสีขาวที่อยู่ในโลโก้เลยไม่โดนลบ

ColorAnalysisService.java Day

analyze(image, excluded) samples up to about 250k pixels, rounds each one into a 16-step color bin and counts them. The bins are sorted by count, with ties broken by RGB so the result is repeatable. detectedColors are the bins that hold at least 1% of the pixels, up to 10, which ignores JPEG noise.

analyze(image, excluded) สุ่มพิกเซลได้ถึงประมาณ 250k จุด ปัดแต่ละพิกเซลลงกลุ่มสีทีละ 16 ระดับแล้วนับจำนวน กลุ่มสีเรียงตามจำนวน ถ้าเท่ากันเรียงด้วยค่า RGB ผลเลยออกมาเหมือนเดิมทุกครั้ง ส่วน detectedColors = กลุ่มที่มีพิกเซลอย่างน้อย 1% (สูงสุด 10 สี) ซึ่งตัด noise ของ JPEG ทิ้ง

Analysis.palette(n) is Median Cut: repeatedly take the heaviest box, sort it along its widest RGB channel and cut it at the weighted median, until there are n boxes. Each box becomes its weighted average color.

Analysis.palette(n) = Median Cut: หยิบกล่องที่หนักที่สุด เรียงตามช่อง RGB ที่กว้างที่สุด แล้วตัดตรงค่ากลางถ่วงน้ำหนัก ทำซ้ำจนได้ n กล่อง แต่ละกล่องกลายเป็นสีเฉลี่ยถ่วงน้ำหนักของกล่องนั้น

VectorEngine.java + AutoTraceVectorEngine.java Day

se233/vectorize/adapter/

VectorEngine is a one-method interface: trace(png, settings, ignoredColor, cancelled) → svg String. AutoTraceVectorEngine implements it by running the external autotrace program:

VectorEngine = interface ที่มี method เดียว: trace(png, settings, ignoredColor, cancelled) → svg String ส่วน AutoTraceVectorEngine implement โดยรันโปรแกรม autotrace ภายนอก:

  • It builds the command as a list of arguments (never one shell string, so there's no command injection): -output-format svg -error-threshold <curveError> [-background-color RRGGBB] -output-file out.svg in.png.
  • stderr goes to a file, so a full pipe can't freeze the process.
  • It waits in 100 ms steps, checking cancel and a 60-second timeout.
  • It treats a non-zero exit code, an empty output, or an output with no <path as an ENGINE error.
  • finally: kills the process if it's still alive and deletes the temporary files.
  • It finds the program from -Dvectorize.autotrace, then the Homebrew paths, then PATH. A missing program gives a friendly "install it" message.
  • สร้างคำสั่งเป็น list ของ argument (ไม่ใช่ string ของ shell ก้อนเดียว เลยไม่โดน command injection): -output-format svg -error-threshold <curveError> [-background-color RRGGBB] -output-file out.svg in.png
  • stderr เขียนลงไฟล์ ถ้า pipe เต็มโปรแกรมก็ไม่ค้าง
  • รอทีละ 100 ms คอยเช็ก cancel และ timeout 60 วินาที
  • exit code ไม่ใช่ 0, ได้ไฟล์ว่าง หรือไม่มี <path → ถือเป็น error แบบ ENGINE
  • finally: kill process ถ้ายังไม่ตาย แล้วลบไฟล์ชั่วคราว
  • หาโปรแกรมจาก -Dvectorize.autotrace → path ของ Homebrew → PATH ถ้าไม่เจอจะบอกให้ไปติดตั้ง
Why an interface? It's the one real replaceable boundary in the project. Another tracer, or a fake one in tests, can be swapped in without touching the pipeline. That is the Adapter pattern.
ทำไมต้องมี interface? นี่คือจุดเดียวในโปรเจกต์ที่ต้องเปลี่ยนตัวได้จริง จะใช้ tracer ตัวอื่นหรือตัวปลอมในเทสต์ก็สลับได้โดยไม่ต้องแตะ pipeline เรียกว่า pattern Adapter

SvgValidationService.java Day

validate(svg) is a safety gate used by both preview and export. It throws an SVG-kind error if:

validate(svg) = ด่านตรวจความปลอดภัย ใช้ทั้งตอนพรีวิวและ export จะ throw error แบบ SVG ถ้า:

  • it has an on* event attribute, an external href, or a javascript:/data: URL;
  • it has zero real shapes.
  • SVG ว่าง หรือ XML พัง (ตัว parser ปิด DOCTYPE ไว้ กันการโจมตีแบบ XXE)
  • root ไม่ใช่ <svg> ใน SVG namespace หรือไม่มีขนาด/viewBox
  • มี <image> (ฝังรูป raster มา = ไม่ใช่ vector จริง), <script>, foreignObject, iframe, object, embed
  • มี attribute on*, href ที่ลิงก์ออกข้างนอก, หรือ URL แบบ javascript:/data:
  • ไม่มี shape จริงเลยสักอัน

ExportService.java Day

exportOne(item, folder, cancelled, stage) handles one image (the coordinator handles the batch):

exportOne(item, folder, cancelled, stage) จัดการรูปเดียว (coordinator เป็นคนจัดการทั้งชุด):

  1. Checks the folder exists and is writable, otherwise it's an OUTPUT error.
  2. If the cached SVG's sourceVersion and PIPELINE_VERSION still match, it reuses the SVG. Otherwise it converts again, so a source file edited after the preview isn't exported stale.
  3. Validates again.
  4. reserve() picks name.svg, name-1.svg, … under a synchronized lock, so two parallel jobs can't pick the same name.
  5. Writes a temp file, then Files.move without REPLACE_EXISTING, so it never overwrites. On failure the temp file is deleted.
  1. เช็กว่าโฟลเดอร์มีอยู่และเขียนได้ ไม่งั้นเป็น error แบบ OUTPUT
  2. ถ้า sourceVersion กับ PIPELINE_VERSION ของ SVG ที่ cache ไว้ยังตรงกัน ก็ใช้อันเดิม ไม่งั้น convert ใหม่ (ไฟล์ต้นฉบับโดนแก้หลังทำพรีวิว ก็จะไม่ export ของเก่าออกไป)
  3. ตรวจ SVG อีกรอบ
  4. reserve() เลือกชื่อ name.svg, name-1.svg, … ภายใต้ lock synchronized งานที่รันขนานกันสองงานจะได้ไม่เลือกชื่อเดียวกัน
  5. เขียนไฟล์ temp แล้วค่อย Files.move ไม่ใส่ REPLACE_EXISTING เลยไม่เขียนทับไฟล์เดิม ถ้าพังก็ลบไฟล์ temp ทิ้ง
Q: Why is there a synchronized here when the rest has no locks? exportOne runs on several worker threads at the same time, and they all share the reserved set.
ถาม: ทำไมตรงนี้มี synchronized ทั้งที่ที่อื่นไม่มี lock? exportOne รันบนหลาย worker thread พร้อมกัน และทุกตัวใช้ set reserved ร่วมกัน

PresetService.java Mona

An extra feature: save and load the current settings as a .properties file. save writes a temp file next to the target, then does an atomic move, so a crash can't leave a half-written preset. load validates every field (a known enum value, a count of 2–5, true or false) and throws an IOException with a user-friendly message. The controller calls it through coordinator.runBackground so the file I/O stays off FX.

ฟีเจอร์เสริม: เซฟ/โหลด settings ปัจจุบันเป็นไฟล์ .properties ตอน save จะเขียนไฟล์ temp ไว้ข้าง ๆ ไฟล์ปลายทางก่อนแล้วทำ atomic move ถ้าแอปพังกลางทางก็ไม่เหลือไฟล์ preset ครึ่ง ๆ กลาง ๆ ส่วน load เช็กทุกช่อง (ต้องเป็นค่า enum ที่มีจริง, จำนวนสี 2–5, true/false) แล้ว throw IOException พร้อมข้อความที่อ่านเข้าใจ controller เรียกผ่าน coordinator.runBackground งานอ่าน/เขียนไฟล์เลยไม่ไปอยู่บน FX

🎤 Quick answers for the demo

🎤 คำตอบสั้น ๆ ไว้ใช้ตอน demo

  • Why doesn't the UI freeze? Every heavy step runs inside a JavaFX Task on an ExecutorService, and the results come back through setOnSucceeded on the FX thread.
  • How is it "real" vector? autotrace traces the outlines into <path>s, and SvgValidationService rejects any SVG that just wraps a bitmap with <image>.
  • How is the background made transparent? Flood-fill a mask from the edges, paint it a unique color, and tell autotrace to ignore that color, so no background shape is created.
  • How are custom colors limited to 2–5? A Median Cut palette, then every pixel is snapped to its nearest palette color before tracing.
  • What if one file is bad? Each file is its own try/catch or its own Task. Errors are collected and the rest continue.
  • When does it run in parallel? Only when ProcessingPolicy says so (more than one image, Medium, Custom, 2 colors). Otherwise jobs go through the single serial thread.
  • ทำไม UI ไม่ค้าง? งานหนักทุกขั้นรันใน JavaFX Task บน ExecutorService แล้วผลส่งกลับมาผ่าน setOnSucceeded บน FX thread
  • ทำไมถึงเป็น vector "จริง"? autotrace ลากเส้นขอบออกมาเป็น <path> และ SvgValidationService ไม่รับ SVG ที่แค่เอา bitmap มาห่อด้วย <image>
  • ทำพื้นหลังให้โปร่งใสยังไง? flood fill ทำ mask จากขอบรูป → ทาด้วยสีที่ไม่ซ้ำใคร → บอก autotrace ให้ข้ามสีนั้น เลยไม่มี shape ของพื้นหลังเกิดขึ้น
  • จำกัดสี 2–5 สียังไง? ใช้ palette แบบ Median Cut แล้วเปลี่ยนทุกพิกเซลเป็นสีใน palette ที่ใกล้ที่สุดก่อน trace
  • ถ้ามีไฟล์เสียไฟล์หนึ่ง? แต่ละไฟล์มี try/catch หรือ Task ของตัวเอง error ถูกเก็บไว้ และไฟล์ที่เหลือทำงานต่อได้
  • รันขนานตอนไหน? เฉพาะตอนที่ ProcessingPolicy อนุญาต (มากกว่า 1 รูป, Medium, Custom, 2 สี) นอกนั้นไปเข้าคิวที่ thread serial ตัวเดียว
